Superstore Sales & Profitability Analytics

A full Power BI project built from the same Superstore dataset as the Excel project — this time focused on a proper star-schema data model, 14 DAX measures, and 3 interactive report pages with drill-through.

The challenge

This project used the exact same raw Superstore data as the Excel dashboard, but the goal was different: build a proper relational data model from scratch (not just clean and visualize), handle real data-quality problems at the modeling level, and produce a full multi-page analytical report with drill-through — all backed by DAX instead of formulas.

The approach

1. Import and shape with Power Query

Imported the workbook's three sheets (Orders, People, Returns), fixed data types (dates, decimals, and kept Postal Code as text to preserve leading zeros), and removed fully blank rows. In the Returns table, I found 800 rows but only 296 unique Order IDs — duplicates were removed so the table could join cleanly into a one-to-many relationship.

2. Build a real star schema

Split the single Orders table into a Fact table and five dimension tables: Dim_Customer, Dim_Product, Dim_ShipMode, Dim_Address, and Dim_Date. Two data-quality problems came up here specifically. First, some Product IDs were linked to more than one completely different product name — so I built a composite key (Product ID + Product Name) instead of trusting Product ID alone. Second, there was no ready-made location key, so I statistically verified that City + Postal Code was 100% unique before using it as a composite key for the address dimension. Dim_Date was built entirely with Power Query M code to guarantee a continuous calendar with no gaps, which I verified was necessary since real gaps existed in the order and ship dates.

3. Add calculated columns for real business logic

Added Shipping Delay (day difference between order and ship date) and a Profitability Category that classifies every row into Loss, Low, Medium, Good, or High profit — not with arbitrary cutoffs, but using statistical quartiles calculated dynamically from the actual positive-margin rows. A supporting Row Margin column and a numeric Rank Profitability column were added to keep the sorting logic correct and avoid a circular dependency between the two.

4. Write 14 DAX measures and build the report

Beyond the basics (Total Sales, Total Profit, Profit Margin %), I built a Running Total using ALLSELECTED, a Year-over-Year Growth % using SAMEPERIODLASTYEAR, a dynamic Top 10 Sales measure driven by RANKX rather than a manual filter, and a text-based Growth Indicator measure that outputs a ready-to-display "▲ 12.3% vs last year" label. All 14 measures live in a separate, empty Measures table to keep the model organized. The report itself spans 3 pages — Executive Analysis, Product Analysis, and a drill-through Order Details page — with slicers synced across all pages, one chart deliberately excluded from a slicer's effect using Edit Interactions, and a bookmark-powered "Reset Filters" button.

Result

A complete analytical Power BI solution — not just a dashboard, but a real data model with documented relationships, 14 working DAX measures, and a tested drill-through path from a product straight to its underlying order-level rows. Along the way I also hit and solved real technical problems: a circular dependency between two calculated columns, a map visual that failed due to a geocoding service issue (replaced with a Treemap with no external dependency), a spiky line chart caused by an unintended day-level drill (fixed by locking the drill level to quarter), and an initially broken YoY calculation that returned impossible values because it depended on MAX() over the full calendar table instead of the actual last date with real data.

What this project demonstrates

  • Designing a star-schema data model from a single flat table
  • Solving real key-uniqueness problems with composite keys, verified statistically before use
  • Writing DAX measures beyond basics: time intelligence, dynamic ranking, and text-based indicators
  • Multi-page report design with synced slicers, controlled interactions, and drill-through
  • Debugging real modeling problems (circular dependencies, broken time calculations, visual failures) rather than avoiding them
